# 公众号内容与排版共创工作流

## 状态

`BRIEFED → LOGIC_DIAGNOSED → FROZEN → STYLE_DEFINED → ASSETS_READY → STRUCTURED → HTML_READY → COVER_READY → PASTE_READY → LEARNED`

不要跨阶段混改。正文没有冻结，不进入精排；个人风格没有定义，不把通用默认值冒充成用户审美；公众号后台与手机预览是最终权威。

## 三种入口

### 完整共创

适用：用户提供初稿、参考图，并允许优化后排版。

从 `BRIEFED` 开始，先诊断内容逻辑和审美方向。诊断结果经用户确认后再修改正文和生成 HTML。

### 正文已冻结

适用：用户明确说“这是最终正文”“不要改文字”。

从 `FROZEN` 开始。内容逻辑只用于标记章节职责、图片证据和风险，不改正文。

### 已有 HTML

适用：用户要求审美诊断、移动端优化或修复公众号粘贴问题。

从 `STYLE_DEFINED` 或 `PASTE_READY` 开始。先锁定已经认可的区域，只修对应问题层。

## 1. BRIEFED｜建立任务卡

至少确认：

```text
文章类型：
目标读者：
希望读者记住／做到：
正文状态：草稿／最终版
允许修改：逻辑／顺序／标题／正文／排版／配图／封面
个人识别资产：
参考旧稿、已发布截图或参考图：
明确不喜欢：
```

先检索用户已有文章、视觉资产和历史修改记录，不要从空白模板开始猜。

## 2. LOGIC_DIAGNOSED｜完成内容逻辑卡

仅在用户允许结构诊断时执行。读取 `content-logic.md`，输出：

- 目标读者与阅读任务；
- 一句话核心命题；
- 当前阅读路径；
- 每个章节的职责；
- 重复内容与证据缺口；
- 建议顺序；
- 需要作者决定的问题。

先给诊断，不默认给全文改写。用户确认后，才按授权范围调整。

放行条件：知道文章为什么值得读、各章节为什么存在、结论由什么证明。

## 3. FROZEN｜冻结正文

1. 保存唯一最终正文；
2. 建立段落清单，标记事实、判断、例子、动作、数字和图片来源；
3. 确认平台标题与正文标题；
4. 正文冻结后，不为了版面好看擅自删句。

## 4. STYLE_DEFINED｜选择首屏版本

用户选择完整同款或无首屏。两版都使用 `xiaowan-preset.md` 与 `layout-standard.md`，按 personalization.md 读取个人配置；只补齐必要信息，不重复询问已有选择。记录作者资产及局部要求。

## 5. ASSETS_READY｜建立证据型配图

每个内容板块填写：

```text
正文判断：
图片必须证明：
首选来源：
需要画面：场景／产品／人物／过程／动作／机制细节
拼图结构：
图注（按需）：
```

优先官方 Campaign、产品页、品牌新闻稿和可靠媒体。若图片不能帮助读者理解正文，不要因为版面空而加入。

## 6. STRUCTURED｜完成手机端视觉脚本

1. 有首屏使用提炼短摘要，无首屏省略该摘要；两版正文均完整保留原文第一段及后文；
2. 标出大章节、子章节、重点句、图片和结尾；
3. 依据同款排版标准设定强调与装饰预算；
4. 两版读取 layout-standard.md，复用同一正文片段；普通间距与局部语义留白分开，不重复叠加；
5. 检查首屏标题是否能在两行内按语义均衡分组，避免为了强调短语拆出明显过短的第三行或 2～3 字末行；
6. 行内重点继承正文字号，只改变字重、颜色或下划线；
- 手机端单段约五六行时检查是否需要按语义拆段；不按字符数自动切句，不靠加粗替代分段，已确认发布稿优先。
8. 结尾可保留外框与署名式文字，只删除点赞、在看、收藏等仿交互控件；
9. 检查相邻屏幕是否连续拥挤或连续空泛；
10. 只看结构稿，也能理解阅读路径。

## 7. HTML_READY｜生成 HTML

1. 使用 `gzh-design` 兼容组件，不重新选择主题；同款参数负责视觉，底层默认不能覆盖；
2. 应用用户偏好与本 Skill 的覆盖规则；
3. 同组多图按内容与手机可读性决定是否合成静态拼图；
4. 输出干净版、预览复制版和发布稳定版；
5. 运行底层 HTML 校验；
6. 在375px和390px检查全篇，运行 audit_preview.cjs，确认识别了全部正文和标题，0段覆盖是失败。

若 `gzh-design` 的自动目录、逐段下划线、引言卡或装饰与同款排版标准冲突，以同款排版标准为准。

## 8. COVER_READY｜封面与发布准备

按 visual-delivery.md 完成已有图审阅、必要找图/生图、横方母图、两种裁切预览、文章摘要及作者信息检查。完整任务主动完成；局部任务不扩张。

## 9. PASTE_READY｜真实粘贴检查

复制进公众号后台后检查：

- 个人识别图片是否存在；
- 所有图片是否正常；
- 拼图是否错位；
- 图标是否乱码；
- 正文字号、颜色与行距是否被改写；
- 是否出现异常空白；
- 手机端标题、重点句和段落是否自然换行；
- 逻辑层级是否仍然可见。

发现问题只修改对应层，不重新设计整篇。

## 10. LEARNED｜把反馈写回系统

比较本地预览、公众号后台与最终发布截图，将修改分为：

- 单篇特殊处理：只留在本项目；
- 内容习惯：写入作者自己的内容逻辑偏好；
- 稳定视觉偏好：写入同款排版标准；
- 必查问题：写入发布清单；
- 作者头像、IP、署名与封面：保存为用户自己的资产，不随公开 Skill 分发。

判断标准：下一篇能否少解释一次、少返工一轮，并且符合用户选择的完整同款或无首屏版本。

实际发布细节、母图双裁切和人工改动保护按 [visual-delivery.md](visual-delivery.md) 执行。

## 范围与文字边界
默认已有长文从FROZEN进入，任务卡与风格卡可内部归纳，不要求用户重复填表。首屏摘要、可选副标题和英文标签属于独立展示文案，按reading-contract.md提炼；原文保持不变，用户禁止新增文字则省略未确认字段。仅本地测试止于本地检查与交付，不执行后台写入；按授权进入PASTE_READY，清单不构成发布许可。样式数值只读layout-standard.md，文字判断只读reading-contract.md。

## 公众号兼容验收与停止条件
只在获准写入草稿时执行。保存前先备份并核对新增人工改动；单一写入链，禁止多个任务同时覆盖同一草稿。先在编辑器验证本次独有的样式标记，再保存、刷新读回全文与样式；不以点过保存或仍读到旧稿认定新稿成功/样式被过滤。停止旧写入的范围只限本篇重复任务，不能取消其他Bot工作。
本轮编辑器实测：普通 `text-decoration:underline 1px #c48a30` 可保存；`text-underline-offset` 未保留；底边框加padding方案在本次粘贴中被删除。这是当前链路证据，不是所有微信版本的永久结论。默认使用已验证普通细线，并说明与本地的间距差异；不循环尝试不可见字符或缩小正文。断行优先调整加粗范围、语义分段、局部左对齐。
发现真问题时先修复授权内的兼容问题，再做一次完整读回；关键方式重复失败时采用已验证降级并说明限制，不无限试写。保存、后台预览、读回后的本地手机宽度渲染、微信真机、公开发布分别记录。最终交付采用同一最新成功保存版本的正文、截图与二维码。用户看过且认可只证明其查看范围，不扩称所有设备已通过。

## 跨 Agent 文件交接与低消耗验收
把一次任务的输入版本、授权范围、验收标准、交付目录一次交清。执行 Agent 单一写入；在同一交付目录维护简短状态文件（任务标识、更新时间、running/blocked/done、阶段、产物路径、阻塞），仅在阶段变化时更新，不为汇报状态反复唤醒模型。接收方优先读取状态与产物，不反复扫描聊天界面；仅在下发任务、明确阻塞或最终视觉核验时使用界面。状态未变化不重复读取全文，不发送重复催办。
完成交付包括最终源稿、保存刷新读回稿、对应后台截图/预览入口、保存时间及差异说明；done不以回复收到或点击保存代替。没有真实通知通道时不得宣称自动唤醒，使用有界文件等待；超时只查询一次具体阻塞。后续仍依既有授权控制草稿、发布与GitHub操作。
